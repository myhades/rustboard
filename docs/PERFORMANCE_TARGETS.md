## 用户目标与基准

- 用户报告当前 Windows 笔记本到 Mac 的 iperf 吞吐约 400 Mbps。尚未由本项目复测；后续需记录方向、单流/多流、参数、设备和网络条件。
- 实际首次文件交付耗时应接近同一环境 iperf 的吞吐上限。必须测到目标文件可用，不能只用 Core 吞吐或 File Provider fetch 回调替代。
- 本地同盘交付的额外耗时应可忽略。区分支持 COW 的元数据克隆、实际字节拷贝和系统交付；不能把 APFS clone 原语的结果推广到任意文件系统或 Windows。
- 长期目标是在现代 CPU、10G 级链路上保持接近链路吞吐，并保持低内存、低 CPU。需要指定机器、CPU、文件系统和存储能力后量化资源预算；现有结果没有证明这一点。

400 Mbps = 50 MB/s ≈ 47.68 MiB/s，1 GiB 仅按有效负载吞吐计算约 21.47 秒。
10 Gbps = 1.25 GB/s ≈ 1192.09 MiB/s，1 GiB 的相同计算约 0.859 秒。
后者是标称速率的理想下界；实际应使用该环境测得的 iperf 有效吞吐。
小文件另测启动延迟，大文件关注稳定吞吐。磁盘写入、持久化要求与系统交付均需纳入解释。

v1 的整数数组 JSON 有编码膨胀和 CPU 成本；固定 64 KiB 串行请求也可能受 RTT 限制。
它们是需要测量的架构约束，不能仅靠解析器微优化就承诺达到 10G。
任何新编码、窗口或协商机制都应另行设计兼容性及测试，不在本轮偷偷修改协议。
发现、配对、NAT/中继策略与已建立连接的数据传输分开测量。

## 验收方法与顺序

1. typed IPC 签名原生读取及正常实体双向三文件/Unicode验收已在后续完成，见 PHYSICAL_INTEROP.md。后续测量继续明确源码、二进制及启动上下文；保持用户自行签名。
2. 在同一机器/网络条件下测双向 iperf 单流及多流、RTT、存储读写；记录版本和参数，区分单连接可用带宽与聚合带宽。
3. 以新 Offer、零预读取开始，测试真实 Windows→Mac 和 Mac→Windows。至少覆盖 4 KiB、64 MiB、1 GiB、多文件，独立验证两端哈希。缓存重复粘贴另列。
4. 拆分发布、握手、网络/IPC、首次字节、最后字节、写入/同步和目标可用时间；报告完整耗时、有效吞吐、相对 iperf 效率以及多次测量的分布。
5. 同时记录各参与进程 CPU 时间、CPU 秒/GiB、平均占用核数、RSS 峰值与并发数。内存应随有界窗口/并发增长，不能随文件大小增长；哈希核验的 CPU 与传输测量分列。
6. 基于证据选择协议/流水线/Core/平台优化，再在 10G 实体链路验收。不能将 loopback 或合成源结果作为真实端到端通过。

“接近”和“低”的具体门槛在专项基线后确定；应同时约束吞吐、CPU、内存、启动延迟及本地交付额外耗时，不能仅追逐单个吞吐数字。
保留按需读取、不预载整个文件、安全配对与身份验证、取消/撤销/过期、失败清理及稳定源语义。
