# 有界二进制传输

2026-10-17。控制协议、Offer、原始 v1 向量不变。TLS 仍为 1.3、双向证书 pin 与签名验证；无明文或认证降级。

## 网络协商

客户端 ALPN 按顺序提供 `rustboard/2`、`rustboard/1`；服务器优先选择共同支持的 v2。
v1 对端继续使用原有 JSON、64 KiB 最大读取。没有共同 ALPN 时拒绝连接。
v2 请求及非 Data 响应仍是四字节大端长度 + JSON，1 MiB 控制帧上限不变。

v2 Data 响应格式：

| 字段 | 字节数 | 编码 |
| --- | ---: | --- |
| 长度 | 4 | 大端 u32，最高位必须为 1；其余 31 位为后续长度 |
| request_id | 8 | 大端 u64 |
| offset | 8 | 大端 u64 |
| eof | 1 | 只能是 0 或 1 |
| bytes | 0..4194304 | 原始文件字节 |

接收方在分配前检查长度不超过本次请求及 4 MiB；校验 request_id、offset、文件大小、EOF 一致性。截断、错误类型或超界使连接失效，不透明重试。

## 活动读取窗口

发布、同步元数据、构造 RemoteSource 不读取主体。首次读取只请求调用者所需范围。
随后连续的 64 KiB 读取可请求最多 4 MiB；短小随机读取不启动窗口。
窗口只在已开始的读取期间生效，每个 RemoteSource 最多保留一个窗口；IPC 最多保留两个源连接/窗口。
这属于有界顺序预读，不能再把每个 64 KiB API 请求声称为恰好 64 KiB 网络读取。
取消时最多存在一个已在途的窗口，不预加载整个文件，也不后台持续填充。

源端仍按最多 64 KiB 调用稳定源，每块检查配对、停止标记、当前 Offer/版本；LocalFile 仍在读前读后检查元数据。
接收端每次交付（包括窗口命中）检查配对、停止/暂停、TTL、当前 Offer；读取及当前 Offer 校验失败丢弃窗口，配对/停止/TTL 检查失败直接拒绝交付。
已在途且已授权的数据不能被远端撤销“收回”，撤销在接收端获知后阻止后续交付。
EOF 从 IPC 缓存移除源；Cancel 清空缓存。随机访问不增加并行连接。

## 本地 IPC

身份认证、Unix socket 权限、Windows Named Pipe ACL 不变。`get_offer` 新增可选 `binary_data:true` 能力。
新消费者仅看到该能力时使用 `read_binary`，字段与 `read` 相同，最大仍为 64 KiB。
成功 Data 使用上述二进制帧；控制/错误仍使用 JSON。未协商不得接受二进制。
旧消费者的 `read` 始终返回原始 JSON；新消费者连接旧 Agent 时因无能力字段而回退 `read`。
两种操作共享 Node 的同一授权、范围验证、取消及传输缓存实现。

## 验证

Rust 测试覆盖 ALPN v1 客户端连接新服务器、二进制范围/截断/EOF、精确 u64、惰性与窗口上限、Offer 撤销及原始向量。
Swift 覆盖未协商拒绝、长度/截断/EOF、精确 u64、JSON 回退以及 hydrate 取消/错误清理。
性能探针与真实 Finder/Explorer 证据分别记录，不能互相替代。
